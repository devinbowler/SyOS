# Design Document: **SyOS** — A Single-Window Work Environment on Debian

*Version 0.3 — final for handoff to Claude Code.*

**Changelog from v0.2:** navigation is now **mouse-first**; custom keybind scheme removed and deferred to a future phase · added §8 "Testing from Windows" (VM workflow before touching real hardware) · added §9 handoff notes — this doc ships alongside `syos-build-plan.md`, the implementation brief for Claude Code.

---

## 1. Vision

A personal work environment that feels like **one instrument panel**, not a pile of applications.

- One frame, always. Everything you open — browser, editor, terminal, calendar — appears as a **tab** (or a pane in a split), never a free-floating window.
- Dense, sharp, dark, terminal-forward aesthetic: small crisp monospace font, 1px borders, zero gaps, one or two accent colors.
- **Mouse-first navigation (v1):** every action — switching tabs, launching tools, closing windows, changing workspaces, starting focus sessions — is reachable by click. A keybind layer is a later, additive phase, not a prerequisite.
- Built-in tools (calendar/scheduler, notes, file/download manager) live in the environment as themed TUI tabs summoned from the bar.
- **Focus enforcement below the UI**: three stacking lockout levels on timers, managed by a root-owned daemon you cannot override mid-session.
- Modern GUI apps (Chrome, Zoom, Slack, etc.) still work — absorbed into the tabbed frame like everything else.
- Installable onto any PC in under 30 minutes from a USB stick + one script. Target fleet: your Zenbook (16:10 HiDPI) and the Panasonic.

### Non-goals (v1)

- Not a distro fork; Debian maintains packages and kernel.
- Not a custom compositor; we configure Sway.
- No custom keybind scheme (deferred — see §4.1).
- No multi-user polish. Built for you.

```
┌─────────────────────────────────────────────────────────┐
│  YOUR LAYER (the "syos" repo)                           │
│                                                         │
│  syos-tui apps ── calcurse/custom scheduler, notes,     │
│                   yazi file mgr, aria2 download queue   │
│  syos-bar      ── clickable control bar: launcher,      │
│                   tool buttons, window controls,        │
│                   workspaces, focus state, sysinfo      │
│  syos-menu     ── fuzzel launcher (opened from bar)     │
│  syos-focusd   ── root daemon: 3-level timed lockouts   │
│  syos-theme    ── fonts, colors, GTK/Chrome theming     │
│  sway config   ── tabbed-by-default, mouse-first,       │
│                   workspace modes, per-laptop scaling   │
│  bootstrap     ── install script + package manifest     │
├─────────────────────────────────────────────────────────┤
│  DEBIAN PROVIDES                                        │
│                                                         │
│  Sway (Wayland compositor) + wlroots                    │
│  PipeWire + xdg-desktop-portal-wlr (screen share)       │
│  systemd, networking, drivers, apt packages             │
│  Linux kernel                                           │
└─────────────────────────────────────────────────────────┘
```

**Key idea:** SyOS is *configuration + small programs + one install script*, not an operating system.

## 3. Core Decisions (locked)

### 3.1 Base: Debian 13 (stable), minimal netinstall
No desktop environment at install; backports enabled for Sway/foot/yazi where stable lags.

### 3.2 Compositor: Sway (Wayland)
Chosen for clean per-output fractional scaling across the two-laptop fleet. Per-machine settings (output scale, font size) live in `local.conf`, generated by an interactive prompt on first bootstrap. Trade-offs and mitigations: screen sharing via PipeWire + `xdg-desktop-portal-wlr` works in Chrome but shares full screens rather than single windows (acceptable in a one-frame UI; XFCE escape-hatch session for emergencies); X11-only apps run via XWayland; Electron apps get Wayland-native launch flags via desktop-entry overrides.

### 3.3 Layout model: tabbed-by-default, splits-by-choice
Default layout is tabbed — every launched app becomes a tab in the current frame. Splits (for the dense multi-column reference look) are created from bar controls; each split region has its own tab stack. Floating is disabled except a whitelist (file pickers, auth dialogs) forced to fixed size/position.

### 3.4 Distribution: Git repo + `bootstrap.sh` (v1), preseeded ISO (Phase 4)
1. Stock Debian netinstall USB, minimal install (~10 min).
2. `sudo apt install git && git clone <repo> syos && cd syos && ./bootstrap.sh`
3. Script installs the manifest, stows configs, installs fonts, runs the per-machine scaling prompt, enables `syos-focusd`, sets Sway autostart, reboots into SyOS.
4. Updates: `git pull && ./bootstrap.sh` (idempotent).

### 3.5 Config management
GNU Stow symlinks; `local.conf` is the only unversioned per-machine file.

### 3.6 Browser: Chrome
Google apt repo (auto-updates), compact UI, forced dark, Wayland flags, always opens as a tab in the Web workspace. Subject of focus Level 3.

### 3.7 Editor: Neovim primary; VSCode retained for the dev-container workflow
Your team flow (VSCode → Dev Containers → moon) maps to the open `devcontainer` CLI: `syos dev <project>` runs `devcontainer up`, opens a shell inside the container, and launches nvim there — moon is invoked from that shell exactly as today. Lost vs VSCode: the `customizations.vscode` extension list (nvim config is mounted instead) and one-click port forwarding (wrapper handles the common case). **VSCode stays installed** as a normal Work-workspace tab for container days and team-facing sessions; zero-risk fallback.

## 4. Features

### 4.1 Navigation: mouse-first (keybinds deferred)

Sway is keyboard-centric by default, so making mouse-only feel first-class is an explicit design surface, not an afterthought:

- **Tabs are natively clickable** — click a tab to focus it. Tab bars are the primary switcher.
- **Window controls on the bar.** Sway tabs have no close buttons, so the bar carries a window-control cluster acting on the focused window: **close ✕**, **split ⬓/⬔**, **move-to-workspace ▸**. One click each.
- **Workspace switching** by clicking the workspace module on the bar (native Waybar behavior); scroll-wheel over the module cycles workspaces.
- **Tool buttons on the bar** (§4.2): one click summons/focuses each built-in.
- **Launcher button** on the bar opens fuzzel (fuzzy app search, mouse-selectable results).
- **Focus sessions started by click:** the bar's focus module opens a small menu — pick level, pick duration, confirm. (Confirm step matters: no accidental 4-hour Level 3.)
- **Drag support:** tabs can be dragged between split regions with the mouse (native Sway behavior).
- Sway's stock default keybinds remain present but undocumented and unrequired — a dormant layer. A designed SyOS keybind scheme is a future phase and will be purely additive.

### 4.2 The Bar (primary control surface)

Waybar, single top bar — with mouse-first navigation this is the cockpit, so it earns more real estate than a typical status bar:

- **Left:** launcher button · workspace modes (Work / Web / Comms / Ops / Board) · window-control cluster (✕ ⬓ ⬔ ▸)
- **Center:** next calendar event (click → opens Board) · focus level + countdown when active
- **Right:** tool buttons — calendar · notes · terminal · files · downloads · monitor · focus menu — then network, volume, battery, clock
- Bar accent color shifts with focus level (green / amber / red) so enforcement state is always visible.

### 4.3 Summonable built-ins

Click the bar button → focus the tool's tab if it exists, else spawn it in its home position. All share the theme.

| Tool | v1 | Custom later |
|---|---|---|
| Calendar/scheduler | `calcurse` | Custom TUI: agenda + timeboxing + "start focus from event" |
| Notes | Neovim notes setup (daily note, fuzzy search) | tuned |
| Terminal | `foot` (Wayland-native, sharp) | — |
| File manager | `yazi` | — |
| Download queue | `aria2` daemon + TUI; bar button offers "add URL from clipboard" | Ops dashboard view |
| Launcher | `fuzzel` from bar button | — |
| System monitor | `btop` | — |
| Dev container | `syos dev` wrapper (§3.7) | — |

### 4.4 Workspace modes

- **1 Work** — nvim, terminals, VSCode when needed
- **2 Web** — Chrome
- **3 Comms** — mail, chat, Zoom
- **4 Ops** — files, downloads, monitor
- **0 Board** — calendar/scheduler dashboard

Apps auto-assigned to their workspace so the layout stays predictable regardless of where they're launched from.

### 4.5 Focus enforcement (`syos-focusd`) — three stacking levels

Root daemon, systemd-managed. Started from the bar's focus menu (or `syos focus <level> <minutes>` in a terminal). `status` and `extend` exist; **no stop command exists.** Sessions end on timer; escape requires reboot — deliberate friction, honestly documented: you own the machine, so the goal is impulse-killing friction, not a literal prison.

Levels stack (each includes everything below):

**Level 1 — No Distractions** *(green)*
Blocks `x.com`, `instagram.com`, `facebook.com`, `youtube.com`, `twitch.tv` (+ CDN/API domains so embeds die), and pornography via the StevenBlack porn hosts list, refreshed weekly and cached. Mechanism: nftables drops + `/etc/hosts` sinkholing + DNS pinned to a focusd-controlled local resolver (changing Chrome's DNS setting doesn't bypass it).

**Level 2 — No AI Assistance** *(amber)* = L1 plus:
AI chat + coding-assist endpoints blocked: `claude.ai`, `api.anthropic.com`, `chatgpt.com`, `api.openai.com`, `gemini.google.com`, Copilot endpoints (`api.githubcopilot.com`, `copilot-proxy.githubusercontent.com`), Cursor, Codeium/Windsurf, Perplexity — maintained in root-owned `profiles.conf`, editable only outside active sessions. Editor gate: nvim (and a VSCode settings toggle) query focusd's socket at startup and refuse to load assist plugins at L≥2; network block is the backstop.

**Level 3 — No Browser** *(red)* = L2 plus:
Chrome cannot run — launch wrapper asks focusd and refuses, a watchdog kills surviving Chrome/Chromium processes, and the binary is made non-executable for your user for the session. Git, SSH, package mirrors, and your startup's APIs keep working, so heads-down coding remains fully viable.

Phase 3: calendar events tagged `[focus:2]` auto-start sessions — your schedule becomes the enforcement.

### 4.6 Theming

Iosevka at 9–10.5pt (size per machine in `local.conf`); near-black `#0d0f12` background, grey-green foreground, desaturated green accent, amber warning. One `theme/palette.conf` source; generator emits configs for foot, sway, waybar, fuzzel, btop, GTK, Chrome theme. Zero gaps, 1px borders, no titlebars.

### 4.7 Modern-app strategy

Apt-first (flatpak fallback), all listed in the manifest so both laptops match. Sway rules absorb every app: right workspace, tabbed, dark. Downloads land in `~/dl`, surfaced in Ops.

### 4.8 Ops & safety net

`syos doctor` (symlinks, package drift, failed services, screen-share health) · hidden stock XFCE session at login as escape hatch · nightly borg backup of `$HOME`, target per machine.

## 6. Roadmap

**Phase 0 — Skeleton.** Repo, `bootstrap.sh`, manifest, stow. Sway boots to a themed tabbed workspace with foot + Chrome as tabs; scaling prompt works. *Done when: fresh Debian VM → clone → bootstrap → reboot → SyOS.*

**Phase 1 — The Panel (mouse-first).** Full Sway config (modes, assignments, splits), Waybar cockpit with launcher / window controls / tool buttons / calendar peek, all built-ins clickable and themed, Chrome + GTK theming, screen-share verification. *Done when: a full mouse-only workday happens inside SyOS.*

**Phase 2 — Enforcement + Dev.** focusd with the three levels (nftables/hosts/DNS pinning, no-stop hardening, editor AI gate, Chrome kill-switch), bar focus menu + accent states, aria2 queue, `syos dev` tested against your startup's repo. *Done when: Level 3 for 90 minutes and Chrome genuinely cannot open without a reboot — and `syos dev` + moon runs your real project.*

**Phase 3 — Make it yours.** Custom scheduler TUI, calendar-triggered focus, Ops dashboard, `syos doctor`, backups.

**Phase 4 — Portability.** Preseeded auto-install ISO; two-laptop fleet polish.

**Phase 5 (someday) — Keybind layer.** A designed hotkey scheme added on top; purely additive, nothing in v1 depends on it.

## 7. Risks & mitigations

| Risk | Mitigation |
|---|---|
| Mouse-only Sway has rough edges (no native close buttons, etc.) | Bar window-control cluster is a Phase 1 deliverable with acceptance criteria, not an afterthought |
| Screen sharing hiccup in a meeting | Verified in Phase 1; XFCE escape hatch at login |
| App misbehaves in tabs | Per-app floating whitelist, fixed size/position |
| Dev-container flow rougher in nvim than expected | VSCode remains installed (§3.7) |
| Lockout during a genuine emergency | Reboot always clears it; sessions don't persist across boot |
| Block lists go stale | Weekly refresh; `profiles.conf` editable outside sessions |
| Config drift between laptops | Everything in git; `local.conf` only unmanaged file |

## 8. Testing from Windows (before touching real hardware)

You can build and validate ~90% of SyOS from Windows using a VM — and it tests the *exact* install path you'll use on the laptops.

**Recommended: VirtualBox (or Hyper-V) + Debian netinstall ISO.**
1. Install VirtualBox on Windows; create a VM (4GB+ RAM, 2+ cores, 25GB disk, EFI enabled, 3D acceleration on).
2. Boot the official Debian netinstall ISO in the VM; do the same minimal install the real laptops will get.
3. Clone the repo and run `bootstrap.sh` inside the VM — a full dress rehearsal of §3.4.
4. Sway runs in VirtualBox via software rendering; bootstrap detects virtualized hardware and sets `WLR_NO_HARDWARE_CURSORS=1` plus a VM-safe output fallback automatically.
5. Iterate: VM snapshots roll back to "fresh Debian" in seconds to re-test bootstrap idempotency — something you can't cheaply do on metal.

**What the VM proves:** install path, bootstrap correctness, the entire UI/bar/tab experience, theming, focusd enforcement (network blocking works in a VM), the dev-container wrapper (Docker inside the VM).
**What it can't prove:** real HiDPI scaling on the actual panels, GPU behavior, battery/suspend, webcam/mic for screen-share. Those are a Phase 1 checkbox on the Zenbook itself.

**Why not WSL2:** WSLg can run individual Wayland apps, but running a full compositor session nested inside it is janky and unrepresentative — wrong tool for testing a desktop environment. WSL2 *is* fine for editing the repo and unit-testing focusd logic if you want a faster loop.
